# 应用示例

以下是根据已记录实践编写的教学示例，不是 Daniel 的原话、真实代码或普遍强制规则。

## 顺序变化：沿调用链验证

某 CLI 原先将收集到的事件按执行顺序排列，新 patch 改为直接流式发送。即使时间戳格式完全正确，也要检查消费者是否依赖原有顺序、等时间戳是否有稳定次序、重试轮次是否仍能区分。

适合的测试输入是乱序到达且包含相同时间戳的不同任务/重试事件，断言完整输出序列。只断言事件数或每行包含时间戳，不能证明顺序契约仍成立。如果产品允许改成到达顺序，则应检查新契约与调用者，而不是一律要求恢复排序。

## 继承测试：用非默认值排除假阳性

父对象配置和子对象默认值都是 `default` 时，子对象等于 `default` 无法证明发生了继承。将父对象设为 `build-bot`，验证子对象得到 `build-bot`。复用现有 fixture 的轻量 decorator；已经在另一层可靠覆盖的逻辑，不必为形式重复跑全链路。

## Review 表达：按证据和影响选措辞

这些片段用于展示表达方式；用于真实 review 时补上实际文件/行号及已核对的上下文，不能照搬示例场景、结论或验证状态。

### 先问必要性，再给理由

“这里还需要再包一层吗？调用方已经把缺失值转成空列表了，这一层只做相同转换。没有其它入口依赖它的话，可以直接复用原来的 helper。”

只在已读到对应调用路径时使用这个理由；入口尚不明确时，先核对而不是推断它无用。

### 已确认的回归，直接说明

“阻塞：`render.go:52–55` 把执行顺序换成了到达顺序。`show.go:90` 直接输出，没有再排序。A 先执行但晚到达、B 后执行却先到达时，静态推演得到 B,A，违反这条命令原有的执行序契约。这里需要保留原排序，并补一个乱序到达的回归测试。”

先确认契约和调用链，才把它写成阻塞；只有真正执行过复现，才能将“静态推演”改成“运行结果”。不把问题藏在客气的疑问里，也不扩大影响范围。

### 用反例追问测试有效性

“父子两边都是 default，这个测试能证明继承发生了吗？即使漏掉赋值也会通过。可以把父对象设成 build-bot，再断言子对象拿到同一个值。”

英文任务可写：“Would this test fail if inheritance stopped working? Both values are default, so it would still pass. Use a non-default parent value and assert the child's value.”

### 具体认可，允许小建议延期

“这次直接复用聚合入口更清楚了。nit，非阻塞：这个注释只是重复变量名，可以删掉；不影响当前行为，也可以后续处理。”

只在确有该改进和维护收益时提；如果用户只要确认的问题，就不额外输出 nit。

### 没有发现问题时

“未发现可确认的问题。看了这次 helper 提取、两个调用方和现有边界测试，行为保持一致；这里只做了静态检查，未运行测试。”

按实际检查范围和执行情况改写，不为了制造个人风格强行追问或凑建议。

## 实现交付

“沿用现有结果类型与聚合入口，增加子结果的转换分支。补了缺失值和失败状态测试；本地目标包测试通过，远端 e2e 尚未验证。矩阵展开是已有独立问题，本次保持原行为并记录限制。”

只有实际完成相应检查时才能使用上述表述；不能照抄测试成功状态。
